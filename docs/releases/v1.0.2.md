# Monita v1.0.2

Monita 1.0.2 simplifies managed updates and returns Docker deployment to one persistent Monita container.

## Software Update

The in-app update flow is now intentionally simple:

1. Monita checks GitHub for the latest published release.
2. The administrator clicks **Update**.
3. The update screen shows progress while the release is downloaded, verified, built, and applied.
4. Monita restarts into the new version and the browser reloads.

The Settings screen no longer exposes GitHub release assets as download buttons. Those files remain attached to GitHub Releases for manual recovery and verification.

## Single-container deployment

Docker Compose now defines only the `monita` service.

There is no persistent `monita-updater` service and no updater shared token. The main container has controlled access to the Docker socket for managed self-updates. When an update is requested, it launches a short-lived `monita-update-worker` container from the currently installed Monita image. That worker exists only for the update operation, preserves the current runtime configuration and persistent data mount, verifies the replacement container, performs automatic rollback when necessary, and removes itself when finished.

At rest, `docker compose config --services` returns only:

```text
monita
```

## Security note

Managed self-updating requires access to the Docker socket, which is equivalent to host-level Docker control. Installations that do not want managed updates can omit that mount and update manually.
